# 브랜드 사전 Phase 2-A — 본문 수집과 단어 사전

작성일: 2026-11-04 · 범위: Phase 2를 둘로 나눈 것 중 **A (수집 + 단어 사전 + 점검 보고서)**. B (후보를 브랜드로 묶어 `brands.json`에 반영)는 A의 데이터를 보고 따로 설계한다.

## 1. 의도와 이유

확장 프로그램의 필터는 `dictionary/brands.json`의 별명 사전에 기대는데, 지금 사전에는 브랜드가 7개뿐이다. 펨코 패션 게시판에서 브랜드는 정식명보다 별명("목동", "얼저고", "무탠", "뉴발")으로 더 자주 불리고, 이런 별명은 사람이 떠올려 적는 방식으로는 다 모을 수 없다.

그래서 게시판 **본문**을 대량으로 모아 단어 사전(word dictionary)을 만들고, 그 안에서 브랜드 후보를 찾는다. 사용자: "제목은 오히려 안중요하고, 게시글 text가 중요해." 브랜드로 묶는 일은 B에서 한다.

이번 범위의 성공은 **내일(2026-11-05) 오전 10시 전까지** 다음 세 가지가 끝나는 것이다:
1. 최근 글 본문이 로컬에 쌓여 있다. 목표는 10만 개다. 다만 **시간이 우선이다** (사용자 결정: "다음날 10시까지 진행"). 수집기는 10만 개에 도달하거나 **2026-11-05 09:40**이 되면 멈춘다. 멈추면 그때까지 모인 양으로 최종 보고서를 만들어 10시 전에 끝낸다 (09:40은 *작성자 판단* — 보고서 생성 시간 여유). 다 못 채운 양은 다음에 같은 명령으로 이어서 받는다.
2. 그 데이터에서 만든 단어 사전(브랜드 후보 순위)이 있다.
3. 2만, 5만, 10만 개 시점의 점검 보고서가 있어서, 규칙이 규모가 커져도 버티는지 아침에 확인할 수 있다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 패션 게시판 최근 글부터 본문을 수집한다. 순서는 파일럿 1시간 → 조정 → 밤새 10만 개다.
- 인터넷이 끊기거나 프로세스가 죽어도 rsync처럼 이어서 받는다. 받은 글은 다시 받지 않는다.
- 2만 / 5만 / 10만 개에서 수집을 멈추지 않고 점검 보고서를 자동으로 남긴다 (사용자 결정).

**비목표**
- 후보를 브랜드로 묶기, 별명 묶기, `brands.json` 수정 — B에서 한다.
- 확장 프로그램 코드 변경, 크롬 웹스토어 배포물에 수집 기능 넣기.
- 댓글 수집.

**반목표 (기술적으로 돌아가도 실패인 것)**
- 수집 때문에 사용자의 펨코 이용이 막히는 것(430). 측정에서 430은 두 번 모두 **429를 받은 뒤에도 계속 요청할 때** 나왔다.
- 다른 사용자의 글이 git이나 공개 저장소에 올라가는 것.
- 밤사이 조용히 멈춰 있는 것. 멈췄다면 왜 멈췄는지가 보고서와 로그에 남아야 한다.

## 3. 확인된 사실 (2026-11-04 사용자 Chrome에서 측정)

- 본문 주소는 `https://www.fmkorea.com/<docId>`다. 본문은 `article .xe_content`, 작성 시각은 `.top_area span.date`에 있다.
- 목록 주소는 `/index.php?mid=fashion&page=N`(카테고리를 지정할 때는 `&category=<id>`)다. 한 페이지에 공지를 빼고 약 20개가 있다. 행 셀렉터는 `src/lib/parser.js`의 `SELECTORS`를 따른다.
- 공지 카테고리 id `210029879`, `209960683`, `5263961399`는 제외한다 (`brands.json`의 `all.excludeIds`).
- 속도: 버킷을 비우지 않은 상태에서 고정 간격으로 초당 0.5 / 0.75 / 1 / 1.5 / 2건을 각 90초씩 보냈고, 모두 100% 통과했다 (최대 응답 870ms). 2건/초보다 빠른 속도는 시험하지 않았다.
- 429 뒤에 계속 요청하면 430(보안 페이지 "에펨코리아 보안 시스템")이 나온다. 두 번 겪었고 둘 다 몇 분 안에 풀렸다.
- 쿠키 없는 봇 요청은 430이다. 로그인된 실제 Chrome 안에서 보내는 `fetch`는 통과한다.
- 본문은 짧다. 518개 표본에서 평균 70자, 자유 카테고리가 약 63%다.
- 518개로 해 본 토큰화 비교:
  - 전체 빈도 상위는 사이즈, 구매, 가격 같은 일반어다.
  - BPE 상위는 어미와 조사다.
  - Kiwi 고유명사(NNP)와 영문(SL)만 거르면 브랜드가 떠오른다 (아셀, 킨치, 모모타로, 이얼즈어고, 얼저고, 무탠, 뉴발, carhartt …).
  - Kiwi는 "블랙야크"와 "k2"를 놓쳤다.

## 4. 동작

### 4.1 실행 환경 (사용자 결정 + 작성자 판단)
- 노트북에서 tmux 세션으로 돌린다 (사용자 제안). 사용자의 맥은 충전기와 외부 모니터에 연결되어 있고, 뚜껑을 닫은 클램쉘 모드로 쓴다 (사용자 확인).
  - 클램쉘 모드는 외부 모니터가 꺼지면 맥이 잠들 수 있다. 확인한 설정은 displaysleep 10분, sleep 1분이다.
  - 그래서 수집기를 `caffeinate -dims`로 감싼다. `-d`가 화면 끄기를 막아서 클램쉘 상태에서도 깨어 있다.
  - 시작 안내에 "밤사이 모니터 전원을 끄거나 케이블을 뽑지 말 것"을 표시한다.
- 원격 서버(ssh)는 쓰지 않는다 (*작성자 판단*). 데이터센터 IP와 새 쿠키에서는 측정한 적이 없다.
- 수집기는 Node 스크립트다. Playwright로 **설치된 Chrome**(`channel: 'chrome'`)을 **전용 프로필 폴더**(`data/chrome-profile/`)로, 창이 보이게 띄운다. 평소 쓰는 Chrome 프로필은 실행 중이면 잠겨 있어서 쓰지 않는다.
- 첫 실행 때 그 창에서 `https://www.fmkorea.com/fashion`이 정상으로 보이는지 확인한다. 로그인이 필요하면 사용자가 직접 한다.
- 모든 요청은 그 탭의 `page.evaluate(fetch(...))`로 보낸다. 측정 때와 같은 출처, 같은 쿠키다.

### 4.2 요청 규칙
- **모든 요청(목록 + 본문)이 하나의 속도 제한을 함께 쓴다.** 고정 간격 0.5초(초당 2건)로 보내고, 동시에 처리 중인 요청은 최대 4개다.
- 수집하는 동안 사용자는 이 노트북에서 펨코를 쓰지 않는다 (사용자 확인). 그래서 측정된 초당 2건을 그대로 쓴다.
- 429를 받으면 새 요청을 즉시 모두 멈춘다. 처리 중인 요청은 끝까지 받되 다시 보내지 않는다. 5분 쉬고 같은 속도로 재개한다.
  - 1시간 안에 429가 세 번 나오면 속도를 초당 1.5건으로 내리고 로그에 남긴다.
  - 1.5건에서 다시 세 번 나오면 초당 1건으로 내린다 (*작성자 판단*).
- 430이나 보안 페이지가 나오면 **종료**한다. 자동으로 다시 시도하지 않는다. 종료 이유를 `state.json`과 마지막 보고서에 남긴다.
- 네트워크 오류나 20초 타임아웃은 서버의 거절로 세지 않는다. 연결이 돌아올 때까지 2초 → 최대 60초 지수 백오프로 기다린 뒤, 같은 요청을 다시 보낸다.
- 측정 때처럼 동시 20개를 한꺼번에 보내는 방식은 쓰지 않는다.
- **로그인 만료·이상 페이지 대비** (*작성자 판단*):
  - 본문 셀렉터가 맞지 않는 응답(로그인 벽, 빈 본문, 구조 변경 등)이 **연속 20번** 나오면 430과 같이 종료한다.
  - 셀렉터가 맞지 않은 글은 "받음"으로 표시하지 않고 `unrecognized.jsonl`에 따로 남겨, 다음 실행 때 다시 받는다.
  - 20번 미만으로 산발적으로 나오는 경우(삭제된 글 등)는 `unrecognized: true`로 `posts.jsonl`에 남긴다.

### 4.3 수집 순서
- 기본: 전체 목록(`category` 없음)의 1페이지부터 차례로 내려간다. 각 페이지의 새 글 번호를 받을 목록에 넣고 본문을 받는다. 목록을 너무 앞서 받지 않도록, 받을 글이 200개 아래로 내려가면 다음 목록 페이지를 받는다.
- 글이 계속 올라오면 목록이 밀려서 같은 글이 다음 페이지에 다시 보인다. 글 번호로 중복을 건너뛰므로 빠지는 글은 없다.
- **깊은 페이지 확인:** 파일럿 전에 `page=5000` 한 페이지를 요청해서 글이 나오는지 본다. 안 나오면 (마지막 페이지 표시 `form.bd_pg[data-last-page]`로 한계를 확인한 뒤) 사용자에게 알리고 수집 순서를 다시 정한다. 그때 쓸 수 있는 방법은 카테고리별 목록이나 검색 기간 나누기다.
- 카테고리 우선순위: 파일럿이 끝나면 카테고리별 "글당 브랜드 후보 언급 수"를 계산한다. 밤샘 수집을 전체 목록 그대로 할지, 비율이 높은 카테고리를 먼저 할지는 그 숫자를 보고 사용자와 정한다. 설정 파일 하나로 바꿀 수 있게 만든다.

### 4.4 저장과 이어받기 (rsync식)
- `data/crawl/posts.jsonl`: 받은 글 한 줄에 하나씩, 덧붙이기만 한다. 필드는 `docId, categoryId, categoryName, title, date, text, imgCount, fetchedAt`이다. 본문 셀렉터가 맞지 않은 글도 `unrecognized: true`로 남겨서 다시 받지 않는다.
- `data/crawl/state.json`: 다음 목록 페이지, 받을 글 번호, 현재 속도, 429 기록, 점검 완료 표시, 종료 이유를 담는다. 매 요청 뒤에 원자적으로 쓴다 (임시 파일에 쓴 뒤 이름 바꾸기).
- 다시 실행하면 `posts.jsonl`의 글 번호 집합을 읽어 건너뛴다. 마지막 줄이 잘린 경우(쓰는 도중 강제 종료)에는 그 줄을 버린다.
- `data/`는 `.gitignore`에 있다 (이번 작업에서 추가).

### 4.5 단어 사전 (Python)
- 입력: `posts.jsonl`의 앞 N줄(점검 시점) 또는 전체.
- 정규화: NFKC 변환, URL 제거, 같은 자모·글자 3번 이상 반복은 2번으로 줄이기, 영문 소문자화.
- 토큰화: Kiwi. 후보 품사는 NNP, SL, 미등록어(NA/UN)이고 2글자 이상만 남긴다.
  - **붙어 있는 토큰 다시 붙이기:** 원문에서 공백 없이 연속한 NNG/NNP/SL/SN 토큰들은 이어 붙인 형태도 후보에 넣는다 (블랙+야크 → 블랙야크, k+2 → k2).
- 점수: 일반 한국어·영어 빈도 대비 상대 빈도(keyness)로 정렬한다. 일반 빈도는 `wordfreq` 패키지의 ko/en 빈도를 쓴다 (*작성자 판단 — 오프라인으로 바로 쓸 수 있는 공개 빈도표*). 일반 빈도가 없는 단어는 최저값으로 둔다.
  - 점수: `log((글 수 기반 빈도 + α) / (일반 빈도 + β))`. α와 β는 파일럿에서 조정한다.
  - 등장한 글이 3개 미만인 후보는 순위에서 뺀다.
- 산출물 `data/lexicon/lexicon-<N>.json`: 단어마다 품사, 출현 횟수, 등장 글 수, 카테고리별 등장 글 수, keyness, 예문 3개(앞뒤 20자)를 담는다.

### 4.6 점검 보고서
- 수집기는 파일럿 종료(약 6,800개), 2만, 5만, 10만 개, 그리고 마감(09:40) 종료 시점에 단어 사전 처리를 **별도 프로세스로** 띄우고, 끝나기를 기다리지 않고 수집을 계속한다 (사용자 결정).
- `data/reports/checkpoint-<N>.md`에 들어가는 내용:
  - **수집 상태:** 경과 시간, 실제 속도, 429/430/네트워크 오류 수, 응답 시간 중앙값·p95의 시간대별 추이, 본문 셀렉터 실패율, 텍스트 10자 미만 비율.
  - **사전 상태:**
    - 상위 후보 100개
    - **알려진 브랜드 재현율:** `brands.json`의 `searchTerms` 전체 + 파일럿 뒤 확인한 브랜드 목록(`data/lexicon/known.txt`) 중 상위 500개 안에 든 비율
    - 이전 점검과의 상위 200개 겹침 비율
    - 카테고리별 글당 후보 언급 수
- 보고서 생성이 실패해도 수집은 계속한다. 실패 사실은 보고서 자리에 남긴다.

### 4.7 실행 흐름 (오늘)
1. 수집기와 사전 처리를 만든다. 핵심 로직(목록/본문 파싱, 이어받기, 속도 제한과 429/430 처리, 정규화, 토큰 붙이기)에 테스트를 붙인다.
2. 깊은 페이지를 확인한다.
3. 파일럿을 1시간 돌린다. 그동안 tmux, caffeinate, 끊김 복구를 실제로 확인한다. 사용자가 와이파이를 잠깐 끄는 시험을 해도 좋다.
   파일럿은 1시간이 지나면 **수집기가 스스로 멈춘다** (`--for 1h` 같은 실행 옵션, *작성자 판단*). 설정을 실행 중에 바꾸는 기능은 만들지 않는다.
4. 파일럿 보고서를 보고 사용자와 카테고리 우선순위, α·β, 불용 고유명사(서울, 일본 등)를 조정한다.
   - `data/lexicon/known.txt`는 이 단계에서 작성자(Claude)가 파일럿 상위 후보 중 브랜드로 보이는 것을 골라 초안을 만들고, 사용자가 훑어본다 (*작성자 판단*). 그래서 2만 개 보고서부터 재현율 지표가 의미를 가진다.
5. 같은 명령을 다시 실행해 밤샘 수집을 시작한다. 이미 받은 글은 건너뛴다.

## 5. 제약
- 수집 데이터(`data/`, `fmf-*.json`)와 펨코 HTML은 git에 넣지 않는다.
- 요청 속도는 초당 2건을 넘지 않는다. 측정되지 않은 속도는 쓰지 않는다.
- 원격 GitHub 동작(푸시, PR)은 사용자에게 먼저 묻는다.
- 새 의존성 (작성자 판단):
  - Node: `playwright` (devDependency, 브라우저는 내려받지 않고 설치된 Chrome을 쓴다)
  - Python: `kiwipiepy`, `wordfreq` — 저장소 안 `tools/lexicon/requirements.txt`와 가상환경(`.venv`, git 무시)
